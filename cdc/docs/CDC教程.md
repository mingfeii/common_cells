## 1. 先搞清楚：到底需要传什么

CDC 是 Clock Domain Crossing，即信号从一个时钟域进入另一个时钟域。假设模块 A 用 `src_clk`，模块 B 用 `dst_clk`，两者没有可用于静态时序收敛的确定相位关系。A 的信号到达 B 时，可能恰好撞上 B 的采样边沿。

即使两颗晶振标称频率相同，也可能需要 CDC。相反，同一个 PLL 派生的两个时钟如果有工具能够建模的确定关系，应先按相关时钟分析；不能仅因为频率不同就把它们全部切成异步路径。

设计前先回答三个问题：

1. 只要知道“目前是什么状态”，还是每次事件都要收到？
2. 几个 bit 是否必须作为同一笔数据一起到达？
3. 接收端忙时，发送端能不能等待？

| 需求 | 例子 | 对应实现 |
| --- | --- | --- |
| 单 bit 慢变化状态，可跳过中间变化 | 设备是否就绪、使能状态 | `cdc_sync_bits`，WIDTH=1 |
| 每个被接受的事件都必须到达 | 启动一次计算、记录一次完成 | `cdc_pulse_handshake` |
| 多 bit 原子快照，允许等待 | 配置字、命令和参数 | `cdc_mcp_handshake` |
| 观察递增位置，可跳过中间值 | 生产进度、FIFO 指针 | `cdc_gray_counter` |
| 一次一笔，追求较小控制开销 | 低速命令邮箱 | `cdc_fifo_1deep` |
| 多笔数据排队，吞吐量较高 | 采样流、数据包片段 | `cdc_async_fifo` |

原文 §3.1 的关键分类就是：允许遗漏中间采样值，还是必须收到每个变化。不能把这两类需求交给同一个简单同步器处理。

## 2. 亚稳态：为什么寄存器会来不及决定 0 或 1

寄存器要求数据在时钟沿前稳定一段 setup 时间，在时钟沿后继续稳定一段 hold 时间。异步输入无法保证总能避开这两个窗口。

违反窗口时，寄存器内部可能暂时处于难以确定的模拟电压状态。这就是亚稳态。它最终通常会恢复成 0 或 1，但恢复时间具有概率性。

亚稳态有两个直接后果：输出可能很晚才稳定；不同下游寄存器可能把它理解成不同的逻辑值。因此，同步器第一级输出只能送给同步链后续一级，不能直接分叉去控制多个业务寄存器。

普通 RTL 仿真里的 `0/1/X` 不会自动模拟这种模拟电压过程。看到波形干净，并不代表已经证明硬件没有亚稳态风险。

### 2.1 两级同步器做了什么

```text
源域寄存器 Q --> [第一级 FF] --> [第二级 FF] --> 目的域业务逻辑
                   dst_clk       dst_clk
                可能亚稳        获得额外恢复时间后再采样
```

第一级接触异步输入；第二级在下一个目的时钟沿采样第一级。两级之间的时间给亚稳态恢复留下余量。两级同步器降低故障概率，不能把概率变成数学上的零，也不保证把窄脉冲捕获下来。

配套 [`cdc_sync_bits.sv`](../rtl/cdc_sync_bits.sv) 支持 `STAGES>=2`，只输出最后一级。`ASYNC_REG` 和禁止移位寄存器提取的属性表达实现意图；具体工具是否识别，必须查看综合和布局报告。

### 2.2 MTBF 应怎样理解

MTBF 是平均故障间隔。常见模型可写成以下比例关系：

```text
MTBF ∝ exp(Tresolve / τ) / (fdst × ftransition)
```

`Tresolve` 是可用于恢复的时间，`τ` 等常数来自实际器件表征；`fdst` 是采样频率，`ftransition` 是异步数据变化率。这个式子用来理解趋势，不能代替特定工艺或 FPGA 的可靠性计算。

目的时钟越快，恢复时间通常越紧；数据毛刺越多，撞上窗口的机会越多；增加同步级数通常能显著提高 MTBF，但也增加延迟。芯片有很多同步器时，系统失效率近似是各个同步器失效率之和，应按系统目标分配预算。

### 2.3 为什么跨域前还要在源域寄存

组合逻辑可能在一次时钟变化后产生多个毛刺。毛刺会提高有效翻转率，还可能被目的域采样成一次不存在的事件。

一般做法是：源域先用寄存器输出干净的电平、request 或 Gray 编码，再跨域。该寄存器用于消除组合毛刺；真正的异步采样仍由目的域同步器负责。

原文对应：§2、§3.2-3.6。

## 3. 单 bit 电平同步：收到状态，不等于收到每次事件

假设 `src_enable` 是源时钟产生的寄存器输出，保持高电平很长时间。将它接到 `cdc_sync_bits` 的 `async_i`，目的域使用 `sync_o`。目的域会晚一些看到变化，但最终能看到稳定电平。

以两级同步器为例，若源信号在目的边沿 D1 前稳定：

| 目的沿之后 | 第一级 | 第二级，即输出 |
| --- | --- | --- |
| D1 | 新值 | 旧值 |
| D2 | 新值 | 新值 |

目的域另一个时序块在 D2 边沿仍读到边沿前的第二级旧值，通常到 D3 才执行使用新值的操作。这是非阻塞赋值的正常语义。若真实硬件第一级在 D1 附近遇到亚稳态，观察到变化的周期还可能推迟；业务逻辑应容忍这种变化。

用同步电平可以表达“现在处于忙状态”；它不能承诺“每次 busy 的上升和下降都被看到”。如果源信号在两个目的边沿之间先高再低，整个变化可能直接消失。

## 4. 脉冲和事件：快到慢为什么容易丢

源时钟周期 4 ns，目的时钟周期 20 ns。一个只高 4 ns 的源域脉冲，可能完全位于目的域两个采样沿之间。即使用五级同步器，也只是把“没有采到的 0”再延迟几级。

```text
目的采样沿      ↑                    ↑
源域脉冲              ┌───┐
                ──────┘   └───────────
目的第一级      一直采到 0
```

### 4.1 开环展宽的成立条件

原文 §4.1-4.4 讨论展宽脉冲，并给出约 1.5 倍目的周期的设计指导和 three-edge 表述。工程上要把最大目的周期、setup/hold、占空比、抖动和裕量一起分析。高电平足够宽，低电平间隔也必须足够长，才能区分连续两个事件。

不要把“1.5 个周期”误读成“对任意相位，必定覆盖三个目的上升沿”。若项目要求实际连续观察到三个上升沿，应另行按照上升沿计数建立更保守的时间条件。

开环方案适合时钟范围确定、输入事件间隔可证明的场景。目的时钟可能暂停、变频，或每个事件都重要时，使用闭环握手更容易维持明确的协议。

### 4.2 Toggle 编码解决了什么，又缺少什么

每次源事件让 `req` 翻转：第一个事件 `0→1`，第二个事件 `1→0`。目的域同步 `req`，再与历史值比较，只要不同就知道发生了事件。

它把一个短脉冲变成能够保持的状态变化。但是，如果源端连续翻转两次，而目的端还没采到第一次，`req` 又回到原值，两个事件就会一起消失。因此，没有反馈的 toggle 仍然需要可证明的发送间隔。

### 4.3 配套方案：带反馈的事件握手

[`cdc_pulse_handshake.sv`](../rtl/cdc_pulse_handshake.sv) 使用 request/acknowledge 两个翻转位：

1. `src_valid && src_ready` 在源上升沿为 1：接受一个事件，翻转 `req`。
2. `req` 通过目的域同步器。
3. 目的域看到 `req_sync != ack`：输出一个目的周期的 `dst_pulse`，并令 `ack=req_sync`。
4. `ack` 同步回源域。源域看到 `req==ack_sync`，重新允许发送。

`src_ready` 的核心判定是“上一笔 request 是否已经得到反馈”。处于忙状态时，request 不会再次翻转，因此不会发生两次翻转相消。

**接口含义：**一次事件指的是一次源端握手，不是 `src_valid` 的一次上升沿。若 `src_valid` 一直保持 1，每次 `src_ready` 重新有效都会再接受一个事件。上游必须在一次握手后撤销 valid，或明确把持续 valid 当作连续事件请求。

若上游不能等待，每个源周期都有不可丢事件，就要增加缓冲或累计计数；一笔容量的握手不能无限吸收突发事件。

目的端不带 `ready`，所以必须能够处理每个 `dst_pulse`。若处理方也可能忙，用下一章的 MCP 邮箱或 FIFO。

原文对应：§4.5、§5.6.1。

## 5. 多 bit 为什么不能逐位打两拍

假设总线由 `0111` 变成 `1000`。四位虽然由同一个源沿触发，但时钟到 Q 延迟、线路延迟和亚稳态恢复时间不可能完全相同。目的端逐位同步后，可能看到新旧位混合的 `0000`、`1111` 或其他值。

每个 bit 分别“稳定”，不等于整组 bit 属于同一笔事务。把 `valid`、操作码和参数分别打拍，也不能保证它们同周期到达。

原文 §5.2-5.5 还讨论控制信号的重汇聚问题。例如必须同时有效的 `load` 与 `enable`，独立同步后可能错开。可在源域把它们合并为一个已寄存事件，目的域收到后再生成本地控制序列。需要先后顺序的两个控制动作，也可以通过一次事件启动目的域状态机来重建顺序。

**允许逐位同步的多 bit 类型只有有明确独立语义的状态位，或满足条件的 Gray 编码等特殊结构。普通配置字、数据字和编码命令应走 MCP 或 FIFO。**

## 6. MCP：数据保持不动，让控制信号慢慢过来

MCP 是 Multi-Cycle Path formulation。在这里，它表示一种 bundled-data 结构：多 bit 数据先保存在源寄存器里，跨域控制经过同步器，目的域等控制到达后再捕获数据。

```text
src_data --> [hold_data] ==================> [dst_data]
                 |                           捕获使能
src_valid --> [req翻转] --> [目的同步器] --> [接收控制]
                 ↑                              |
                 +----- [源同步器] <--- [ack] ---+
```

双线表示数据本身没有逐位同步。安全来自三个条件共同成立：数据先在源端寄存；在途期间一直保持；目的采样发生前，所有数据位的物理路径已经完成建立。

### 6.1 配套 MCP 邮箱的完整生命周期

[`cdc_mcp_handshake.sv`](../rtl/cdc_mcp_handshake.sv) 有标准的两侧 `valid/ready/data` 接口：

| 步骤 | 发生的动作 | 必须维持的条件 |
| --- | --- | --- |
| 源端接受 | 将 `src_data` 写进 `hold_data`，翻转 `req` | 仅在 `src_valid && src_ready` 时发生 |
| 请求在途 | `req` 经过目的同步器 | `hold_data` 保持不变 |
| 目的端捕获 | `dst_data<=hold_data`，`dst_valid<=1` | 物理数据路径满足延迟预算 |
| 目的端等待 | `dst_valid=1`，等待 `dst_ready` | `dst_data`、`hold_data` 都保持 |
| 目的端消费 | `dst_valid && dst_ready` | 更新 `ack`，撤销 `dst_valid` |
| 反馈在途 | `ack` 同步回源域 | 此时源仍然不能改 `hold_data` |
| 源端重新可用 | `req==ack_sync` | 下一笔可以覆盖 `hold_data` |

本实现的 ACK 表示下游**已经消费**数据。它比“看到请求就 ACK”更保守，但允许下游任意背压，接口也容易理解。

### 6.2 两级同步时逐沿理解

设源端已经装载数据并翻转 request，D1 是第一个能可靠采到新 request 的目的上升沿：

| 时刻 | 目的同步器 | 邮箱业务动作 |
| --- | --- | --- |
| D1 后 | 第一级新值，第二级旧值 | 尚不捕获 |
| D2 后 | 第二级成为新值 | 本沿业务逻辑仍看到旧的第二级 |
| D3 后 | request 已可使用 | 捕获 `hold_data`，置 `dst_valid` |
| D4 或更晚 | `dst_valid` 有效 | 在 `dst_ready=1` 的边沿消费并反馈 |

在仿真波形中，寄存器值在边沿后更新；“边沿之后 valid 为 1”和“这个边沿已完成 valid/ready 握手”要区分开。

### 6.3 MCP 的物理条件

如果把 `hold_data` 到 `dst_data` 的走线任意拉长，数据仍可能赶不上捕获沿。控制打两拍不会自动保证任意长数据线都安全。

对这个实现，`STAGES=2` 时从源端启动到最早捕获有约两个目的周期的下界，再扣除时钟不确定性、时钟到 Q、setup 和工程裕量。实际项目可采用**小于一个最短目的周期**的更保守数据路径预算，减少边界分析复杂度；预算的起止点定义要与工具一致。

应为 bundled-data 路径建立明确的最大延迟约束并检查报告。不要一边把整个异步时钟对设成 false path，一边误以为低优先级 max-delay 仍在生效。

MCP 架构也不等于直接写一条 `set_multicycle_path 2`。异步时钟没有固定相位，约束应体现数据保持协议和真实的物理时间预算。

### 6.4 如何选择 MCP

一个 32 bit 配置寄存器偶尔更新一次，且每次更新都要求参数整体一致，MCP 很合适。若每个源周期都产生一笔新数据，MCP 每笔要等待往返反馈，吞吐量往往不够，应选择多项异步 FIFO。

原文对应：§5.6、§12.2。配套实现将原文的发送/接收状态机整合成 request/ack 等价关系，并使用显式宽度参数和显式连接。

## 7. Gray 编码：安全地观察递增位置

二进制的 `0111→1000` 同时改变四位。反射 Gray 码在相邻计数间只改变一位，例如：

| 二进制计数 | Gray |
| --- | --- |
| 0 | 0000 |
| 1 | 0001 |
| 2 | 0011 |
| 3 | 0010 |
| 4 | 0110 |
| 5 | 0111 |
| 6 | 0101 |
| 7 | 0100 |
| 8 | 1100 |

转换关系是 `gray = bin ^ (bin >> 1)`。恢复第 i 位二进制，可对 Gray 从最高位到第 i 位做异或。本项目用常量生成循环：`dst_bin[b] = ^(dst_gray >> b)`，避免动态范围 part-select 的语法问题。

### 7.1 源端必须寄存 Gray 输出

[`cdc_gray_counter.sv`](../rtl/cdc_gray_counter.sv) 同时维护二进制寄存器和 Gray 寄存器，使用下一拍二进制值产生下一拍 Gray 值：

```text
next_bin  = src_bin + src_inc
next_gray = next_bin XOR (next_bin >> 1)
在同一个源时钟沿把 next_bin、next_gray 分别寄存
```

每次只能不变或加 1，允许自然模 `2^WIDTH` 回绕。不能直接把任意跳转的二进制值转换成 Gray，便认为跨域就安全。一次跳 5 步时，Gray 位仍可能多位同时变化。

组合 Gray 编码输出也可能产生毛刺。应跨域的是寄存后的 Gray 输出，而不是正在变化的二进制总线经过组合异或后的直接输出。

### 7.2 目的端可以跳过中间计数

源域已走到 8，目的域可能先看到 3，再看到 7，再看到 8。只要用途允许中间值被跳过，这可以接受。FIFO 用它观察对方指针，过时的位置通常只会让本地判断更加保守。

**只检查源端相邻 Gray 值的变化位数。**目的端两次采样可能跨过多个源计数，因此目的端 Gray 相邻采样不一定只差一位。用 `$onehot0(dst_gray ^ $past(dst_gray))` 检查目的端通常会误报。

目的端 Gray 解码是组合逻辑，在目的边沿后可能短暂变化。本项目 `dst_bin` 用于由目的时钟采样的同步逻辑，不应直接用作异步无毛刺控制或生成时钟。

### 7.3 Gray 码也需要物理约束

如果上一笔变化走了一条极慢的线路，而下一笔变化走了快线路，两次变化可能在目的第一级输入处交错。应约束 Gray 寄存器到对端第一级同步器的各位延迟和位间偏斜，使连续更新不会在接收端形成错误重叠。

常见保守方法是使用小于最短源更新间隔的路径/偏斜预算，再留裕量。FIFO 两个方向应分别按各自源时钟的最短更新周期分析，不能只用一个固定“慢时钟周期”。

### 7.4 Gray 计数器不等于不会丢事件的队列

如果通过两个快照相减统计事件，必须保证两次可靠快照之间的真实增量小于 `2^WIDTH`，否则无法区分“没发生事件”和“发生了一整圈”。若目的时钟可能无限停止，有限位宽计数器也无法提供无限事件保存能力。

原文对应：§5.7。原文的两种计数风格分别是在 Gray 上递推，以及同时保存二进制与 Gray。本项目采用后者。

## 8. 论文中的双寄存器 FIFO：物理两格，逻辑一笔

[`cdc_fifo_1deep.sv`](../rtl/cdc_fifo_1deep.sv) 对应 §5.8.2 和 §12.3。

有 `mem[0]`、`mem[1]` 两个位置，写指针和读指针各只有一位。每次写或读都把对应指针翻转。这里没有额外的回绕位，所以不能用它区分一般意义上的“两格都满”和“两格都空”。协议通过限制最多一笔在途避免这种歧义。

核心关系：

```text
wready = (wptr == 已同步回来的 rptr)
rvalid = (rptr != 已同步过来的 wptr)
```

把一次完整传输展开：

| 动作 | 写指针 | 读指针 | 含义 |
| --- | --- | --- | --- |
| 复位后 | 0 | 0 | 空，可以写 |
| 写入 A 到 mem[0] | 1 | 0 | 已有一笔，暂时不能再写 |
| 写指针到读域 | 1 | 0 | 读域知道 mem[0] 有效 |
| 读端消费 A | 1 | 1 | 本地变空，反馈读指针 |
| 读指针到写域 | 1 | 1 | 可再次写入，目标已经是 mem[1] |

第二个寄存器使已消费后的读地址移动到下一个位置。下一笔数据可以在该位置准备好，再由同步写指针宣布有效。读端不需要像本项目 MCP 邮箱那样再把总线复制到一个专门的目的输出寄存器，因此控制路径更短。

`rdata` 是异步读、首字直出的 FWFT 形式：只在 `rvalid=1` 时有有效含义；读端在 `rvalid && rready` 的读上升沿取数。在 `rvalid=0` 时，`rdata` 可以是旧值或 X，不能拿它判断 FIFO 内容。

## 9. 通用异步 FIFO：用排队换取吞吐量

[`cdc_async_fifo.sv`](../rtl/cdc_async_fifo.sv) 是在原文 §5.8.1 提示的 FIFO 路线上补充的完整小容量实现。原论文并未在该节给出这份通用 FIFO RTL。

深度 `DEPTH=2^ADDR_WIDTH`，至少为 2。每个指针有 `ADDR_WIDTH+1` 位：低位寻址，额外一位区分回绕。二进制指针留在本地做加法和寻址，寄存后的 Gray 指针跨域。

```text
写域：wbin -> 地址 -> 双端口寄存器存储 <- 地址 <- rbin：读域
       |                                      |
     wgray ----> 读域同步器        写域同步器 <---- rgray
       ↑                                      ↑
  本地算是否满                            本地算是否空
```

### 9.1 空的判断

读指针 Gray 等于已经同步过来的写指针 Gray，表示本地认为没有可读数据。因此 `rvalid=(rgray!=wgray_sync)`。

写入刚发生时，读域还没看到新写指针，可能暂时继续报空。这样会晚读几拍，但不会读到尚未发布的数据。

### 9.2 满的判断

二进制上，写指针比读指针超前一整圈，即差 `DEPTH`，表示满。转换为反射 Gray 码后，满条件是：写 Gray 等于同步读 Gray 的**最高两位取反，其余位不变**。

本项目采用当前指针组合比较，`wready` 表示当前状态还能不能接受一笔。接受最后一个空位的数据后，写指针更新，`wready` 随之变低。另一种常见实现使用 next 指针产生寄存 full 标志，两者不能在同一套逻辑中随意混用。

读域已经消费但读指针还没返回时，写域可能暂时继续报满。这个保守延迟不会导致覆盖未读数据。

### 9.3 为什么数据不用逐位同步

写入内存后，写指针要经过同步器，读端才知道对应位置有效。只要物理数据路径赶得上 valid 所允许的最早采样沿，读取时数据已经稳定。协议保证未读位置不会被写端覆盖。

这与 MCP 有共同点：跨域的是“稳定数据加同步控制”，而不是让所有数据位各自自由同步。异步读数据路径仍然需要延迟预算，不能把它无限切掉。

### 9.4 存储类型必须匹配接口

本实现是源时钟写入、组合异步读取，适合小型寄存器或支持异步读的分布式 RAM。它不承诺推断出 FPGA 块 RAM。

如果换成同步读 RAM，地址发出后数据会晚一拍或更多拍。必须增加预取、输出寄存和对应 valid 管理，重新验证背压和空边界；不能仅替换存储语句。

原文参考文献 [1] 是作者更早的异步 FIFO 专题论文；本教程保留这一出处，但当前实现与测试以随附文件为准。

## 10. 复位也是跨域协议的一部分

两边的 request/ack、读写指针和同步器历史必须从一致状态开始。如果只清零某一侧，另一侧可能把指针或 toggle 的变化误认为一笔新传输，也可能永久等待一个不会再来的反馈。

本项目规定：所有关联域来自同一个异步复位输入 `arst_n`，每个域用自己的 [`cdc_reset_sync.sv`](../rtl/cdc_reset_sync.sv) 同步释放。复位发生时，异步断言会立即把本域复位输出拉低；释放需要本地若干个时钟沿。

```text
                   +--> 复位同步器(src_clk) --> src_rst_n
共同 arst_n -------+
                   +--> 复位同步器(dst_clk) --> dst_rst_n
```

两边释放的实际时刻可以不同。已释放的一边即使开始等待，另一边释放后也能从共同清零的协议状态继续工作。还没释放的域不得让业务逻辑发起有效消费。

**共同复位的含义是清空通道。**复位前已接受、尚未交付的数据和事件可以丢弃。存储数组不必清零，因为复位后指针和 valid 把旧内容标记为无效。

如果系统必须支持一侧独立复位、另一侧不停机，需要增加链路重新对齐/epoch 或 flush 协议，并定义上游重发策略。本项目现有模块不提供这种语义。若复位期间两边都能完整共同断言，而某一时钟暂停，同步释放会自然等待该时钟恢复。

## 11. 接入 ready/valid：只在本地边沿数握手

源端在 `src_valid && src_ready` 的源时钟上升沿完成接受。目的端在 `dst_valid && dst_ready` 的目的时钟上升沿完成消费。

上游需要保持 `valid=1` 和数据不变，直到发生握手；下游背压时，模块保持输出 valid 和数据。握手后，上游可以在下一源周期准备下一笔，具体能否接受由 ready 决定。

`src_ready` 是源域信号，`dst_valid` 是目的域信号。不要跨过边界把对面的 ready 直接接回本域业务逻辑。CDC 模块内部已经处理同步反馈。

复位期间，本项目 ready/valid 或事件脉冲被抑制；空闲 FIFO 数据线仍可能是 X。系统应以有效信号为准，不应通过给所有数据线硬加复位来掩盖接口误用。

完整可综合集成例子见 [`examples/cdc_mailbox_example.sv`](../examples/cdc_mailbox_example.sv)，接口汇总见[代码接口手册](代码接口与集成.md)。

## 12. 布局与时序约束：RTL 正确之后还要完成的工作

原文 §6 强调按时钟域命名和分区。实用做法是将正常业务模块做成单时钟模块，把异步输入集中在少量 CDC 模块中。

| 路径 | 检查要求 |
| --- | --- |
| 异步控制源到同步器第一级 D | 不要求满足固定相位 setup/hold；明确标识异步入口 |
| 同步器一级 Q 到二级 D，及后续级 | 正常检查 setup/hold，缩短布线以保留恢复时间 |
| 源 Gray 寄存器到对端第一级 | 最大延迟/总线偏斜预算，避免连续更新交错 |
| MCP 保持寄存器到目的捕获寄存器 | 数据必须在最早合法捕获前到达 |
| 异步读 FIFO 存储到消费寄存器 | 数据在 valid 允许的采样前建立，消费寄存器往往位于模块外 |
| 目的同步后的业务路径 | 正常按本域时钟进行 STA |

`set_clock_groups -asynchronous` 很方便，但通常会切掉整对时钟之间的路径。不同工具的例外优先级不同，必须确认它没有覆盖 bundled-data 或 Gray 总线的物理约束。项目中应采用经过工具文档验证的组合，而不是把多份网上 SDC 直接叠加。

约束起点、终点需要从综合网表确认，尤其是寄存器数组命名和存储推断之后。属性不等于约束，约束不等于已经生效：要检查匹配对象数量、有效 timing exception 和实际最差路径。

具体实施要求见 [`constraints/README.md`](../constraints/README.md)。该目录给出预算和验收方法；没有目标芯片、综合网表和工具时，不提供声称可直接签核的通用 SDC。

## 13. 仿真：用自检证明事务行为

测试程序为 [`sim/tb_cdc.sv`](../sim/tb_cdc.sv)，运行入口为 [`sim/run.ps1`](../sim/run.ps1)。测试没有将生产 RTL 替换成随机延迟版本。

### 13.1 事务记分板

发送端只在本地真正发生 `valid && ready` 时，把数据加入参考队列；接收端只在本地真正消费时，取出队头逐笔比较。这样可以发现丢失、重复、乱序、位错误和无数据时凭空读出。

邮箱、单笔 FIFO、通用 FIFO 都使用同样的外部事务检查，不靠复制 DUT 内部指针算法来生成预期结果。

### 13.2 定向阶段加可复现变化流量

每次测试先阻止读取，把通道填满，核实能容纳的笔数；然后停止新增并排空；接着运行确定种子的伪随机发送/背压，最后再次排空。

输出背压期间会检查 `valid` 不能消失、数据不能变化。事件通道比对已接受事件数与收到脉冲数。Gray 计数器检查源端计数和相邻 Gray 变化，并核对目的同步流水线及停止更新后的收敛。

每组参数跑两轮完整流程，并在额外活动流量期间共同复位，让通道清空后重新运行。测试覆盖快到慢、慢到快、同边沿、1 bit 数据/深度 2 和三级同步。

### 13.3 波形应该看什么

MCP：看 `hold_data` 从源握手到 ACK 返回是否保持；看 `req` 先到 `req_sync`，再置 `dst_valid`；看目的 ready 拉低时输出是否冻结。

单笔 FIFO：看写指针每笔翻转一次；读取之前 `wready` 不会再开放；读指针返回后才允许下一笔。

通用 FIFO：看满时写指针停止，空时读指针停止；读写速率不同但数据顺序保持；一方指针回传延迟只产生保守等待。

### 13.4 仿真证明不了的内容

这些测试验证数字模型的功能和协议，并非穷举证明。RTL 仿真不测量真实亚稳态恢复常数，不证明 MTBF，也不会自动检查布局后总线偏斜。当前回归使用零延迟 RTL，没有进行门级 SDF、形式验证或某个目标器件的综合/布局签核。

实际工程还需要静态 CDC 检查、RDC/复位检查、约束审查、STA，以及实际器件同步器可靠性评估。原文 §7.7 的随机周期延迟模型可以作为额外验证技术，但它不是最终硬件实现，也不能代替这些检查。

## 14. 门级仿真为什么会出现大片 X

原文 §7 讨论门级同步器第一级故意面对异步输入，因此 setup/hold 违规可能触发单元模型 notifier，继而把 Q 变成 X。X 又经过数字模型传播，可能淹没功能波形。

应定位被认可的同步器首级，按目标库和仿真工具处理其异步输入 timing check/notifier，或使用厂商同步器模型。后续级之间和正常业务路径的时序检查应保留。

不要全局关闭 timing check 来获得“干净波形”。也不要认为 force 首级 notifier 后就证明了硬件安全；这只是让数字门级仿真可以继续检查功能，真实可靠性仍靠 MTBF、实现约束和报告。

原文针对 2008 年工具和厂商能力的评论具有时代背景，不宜直接当成当前厂商功能列表。

## 16. 实际选型示例

**外设工作模式变化：**若只关心当前启用还是禁用，并允许短暂模式变化被跳过，使用单 bit 同步器。若“启用一次”本身就是不能漏的命令，改用事件握手。

**32 bit 配置更新：**使用 MCP。源端等 ready 后提交整个配置字，目的端在 ready 时一次性消费。若配置由多个寄存器组成，先在源域打包成一笔快照，避免不同版本混合。

**ADC 连续采样：**使用足够深的异步 FIFO，并根据生产/消费速率和最长背压时间计算容量。FIFO 只能吸收有限突发；长期平均生产率高于消费率时，任何有限深度最终都会满。

**观察累计完成数量：**允许跳采样且能界定回绕范围时，使用 Gray 计数器；若每个完成事件还带有结果数据，需要 FIFO 或握手，单独传一个计数器不能保存这些结果。

**低速命令通道：**MCP 和单笔 FIFO 都适合。优先按照下游是否需要寄存输出、吞吐量和实现资源选择；需要多笔并发时直接使用多项 FIFO。
